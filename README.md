СЕРВИС ПРОДАЖИ БИЛЕТОВ НА СОБЫТИЯ

Учебный командный проект: реляционная база данных на PostgreSQL 18 с закрытым SQL API, фиксацией истории цен, защитой от двойных продаж и автоматическим снятием просроченных броней.

1. Условие задания и бизнес-правила
Заказчик: билетный оператор (концерты, театры, кино).
Основные требования и реализованная логика:
- Структура залов и событий: поддержка площадок, залов, категорий мест (Обычная, VIP) и привязки рассадки к конкретным мероприятиям.
- Бронирование с ограничением по времени (TTL): одна бронь оформляется на одно место и действует ровно 15 минут. Просроченные брони снимаются при новых попытках бронирования либо фоновой функцией expire_bookings().
- Защита от двойных продаж: одно место на одно событие не может быть продано дважды даже при параллельных запросах — используются блокировки строк (SELECT ... FOR UPDATE), блокировки по ключу операции (pg_advisory_xact_lock) и уникальные частичные индексы на уровне БД.
- Динамическое ценообразование и история цен: если до начала мероприятия остается 24 часа или меньше, цена для новых броней увеличивается на 20%. Зафиксированная цена сохраняется в price_versions и привязывается к брони (price_snapshot), поэтому дальнейшее изменение базовой цены не влияет на уже созданную бронь.
- Оплата и возврат: платежный шлюз имитируется. Повторный запрос оплаты или возврата с тем же ключом операции (operation_key) не создает дублей и возвращает прежний результат. Полный возврат билета разрешен до начала события — старый билет остается в истории со статусом returned, а место возвращается в продажу.
- Закрытый SQL API: сервисная роль не имеет прямых прав на изменение таблиц — все операции проходят строго через функции с SECURITY DEFINER.

2. Команда, роли и зоны ответственности
1) Дарья — Аналитик / Владелец продукта
   Формулировка бизнес-требований, правил бронирования, возврата и динамических цен; приемочный контроль.
2) Михаил — Архитектор данных
   Проектирование ER-модели, нормализация, ключи и ограничения целостности (1_schema.sql, 2_seed.sql).
3) Алексей — Разработчик БД
   Транзакционные функции бронирования, оплаты, возврата и представления отчетов (3_booking.sql, 4_payment_refund.sql, 6_reports.sql).
4) Дана — Администратор БД (DBA)
   Настройка ролей и прав доступа (7_access.sql), регламент резервного копирования и фоновой очистки броней, контроль индексов и ограничений в таблицах.
5) Сергей — Тестировщик данных (QA)
   Автотесты логики, негативных сценариев, целостности модели и нагрузочное тестирование (5_check_purchase.sql, 8_regression.sql, 9_qa_negative_checks.sql, 10_load_test.py).

3. Состав репозитория
1_schema.sql              - создание 12 таблиц, внешних ключей, индексов и проверок
2_seed.sql                - наполнение базы тестовой площадкой, залом, местами и двумя событиями (через 7 дней и через 12 часов)
3_booking.sql             - функции reserve_seat() и expire_bookings()
4_payment_refund.sql      - функции pay_booking() и refund_ticket()
5_check_purchase.sql      - базовый сквозной тест покупки, возврата и новой брони с откатом (ROLLBACK)
6_reports.sql             - представления event_occupancy, sales_operations, price_history и контрольные запросы отчетов
7_access.sql              - создание ролей (ticket_service, ticket_reporter, ticket_maintenance) и настройка прав доступа
8_regression.sql          - 7 групп автоматических регрессионных проверок (логика, цены, целостность, права)
9_qa_negative_checks.sql  - расширенные негативные тесты (наценка +20%, NULL, конфликты ключей, возврат после старта, изоляция ролей)
10_load_test.py           - нагрузочный скрипт на Python через pgbench (1000 попыток: 20 клиентов x 50 транзакций)

4. Инструкция по развертыванию и использованию
Шаг 1. Создание новой базы данных
Скрипты предназначены для установки на новую пустую базу. Схему и функции должен создавать один владелец с правом CREATEROLE:

    createdb -U postgres ticket_system_v2

Шаг 2. Последовательный запуск SQL-скриптов
Выполните скрипты строго в порядке их нумерации:

    psql -U postgres -d ticket_system_v2 -X -v ON_ERROR_STOP=1 -f 1_schema.sql
    psql -U postgres -d ticket_system_v2 -X -v ON_ERROR_STOP=1 -f 2_seed.sql
    psql -U postgres -d ticket_system_v2 -X -v ON_ERROR_STOP=1 -f 3_booking.sql
    psql -U postgres -d ticket_system_v2 -X -v ON_ERROR_STOP=1 -f 4_payment_refund.sql
    psql -U postgres -d ticket_system_v2 -X -v ON_ERROR_STOP=1 -f 5_check_purchase.sql
    psql -U postgres -d ticket_system_v2 -X -v ON_ERROR_STOP=1 -f 6_reports.sql
    psql -U postgres -d ticket_system_v2 -X -v ON_ERROR_STOP=1 -f 7_access.sql

(При запуске через pgAdmin или DBeaver выполняйте файлы в том же порядке; при возникновении ошибки сначала выполните ROLLBACK;)

Шаг 3. Примеры основных операций SQL API

    -- Посмотреть заполняемость залов и доступные места
    SELECT * FROM public.event_occupancy;

    -- Забронировать место (user_id = 1, event_seat_id = 1) -> возвращает ID брони
    SELECT public.reserve_seat(1, 1);

    -- Оплатить бронь с уникальным ключом операции -> возвращает ID билета
    SELECT public.pay_booking(1, 'payment-key-001');

    -- Оформить возврат билета до начала события -> возвращает ID операции возврата
    SELECT public.refund_ticket(1, 'refund-key-001');

    -- Снять просроченные брони
    SELECT public.expire_bookings();

Шаг 4. Запуск автотестов и нагрузочной проверки
Автотесты запускаются после 7_access.sql (все изменения в конце откатываются через ROLLBACK):

    psql -U postgres -d ticket_system_v2 -X -v ON_ERROR_STOP=1 -f 8_regression.sql
    psql -U postgres -d ticket_system_v2 -X -v ON_ERROR_STOP=1 -f 9_qa_negative_checks.sql

Нагрузочный тест запускается только на отдельной тестовой базе (не на рабочей), пароль передается через штатный файл pgpass:

    python 10_load_test.py --database ticket_test --user postgres --bin "C:/Program Files/PostgreSQL/18/bin"
